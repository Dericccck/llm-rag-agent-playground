# 10 AI Agents Production 学习摘要

## 对应 Notebook
- `10-semantic-kernel.ipynb`

## 这一节在做什么
这一节是在讲 Agent 进入生产环境后一个非常现实的问题：
- 如果主服务挂了怎么办？

所以它重点演示的是：
- 容错
- 服务降级
- 故障转移

## 这里要分清三个角色

### `qwen-max` / `gpt-4o-mini`
- 负责理解用户订票请求
- 负责根据工具返回结果决定下一步策略
- 负责把故障处理后的结果用自然语言解释给用户

### `get_flight_times`
- 这是主查询工具
- 在这个 notebook 里被故意设计成失败

### `get_flight_times_backup`
- 这是备份工具
- 当主工具失败时，由 Agent 切换过来使用

## 这个 notebook 里的实现工序

### 1. 定义插件和两套工具
插件里有两个核心航班查询函数：

#### 主函数
- `get_flight_times`
- 故意返回 `HTTP ERROR 404`

这不是 bug，而是故意用来模拟真实生产环境里的外部服务故障。

#### 备份函数
- `get_flight_times_backup`
- 提供同类航班数据，但走备用路径

### 2. 用提示词写清楚故障处理规则
系统提示词里明确告诉 Agent：
- 先调用主工具
- 如果主工具返回错误，就立刻调用备份工具
- 给用户一个积极、自然的解释
- 不要把内部故障暴露得太糟糕

也就是说，这里的 fallback 策略一部分是代码设计，一部分是提示词约束。

### 3. 创建 Agent
创建 `TravelAgent`，把两套工具都挂进去。

### 4. 用户发起订票请求
例如：
- `Book me a flight to Barcelona`

### 5. Agent 先试主服务，再自动切备份
执行时大致流程是：
- 模型读取用户需求
- 先调用 `get_flight_times`
- 发现返回的是错误信息
- 按提示词规则改调 `get_flight_times_backup`
- 取得可用航班数据
- 生成最终回答

## 整个工序可以简化成
用户请求 -> Agent 调主工具 -> 主工具失败 -> Agent 判断需要 fallback -> 调备份工具 -> 拿到可用结果 -> 向用户输出稳定回答

## 这一节的关键收获
- Production Agent 的关键不是“平时答得多好”，而是“出问题时还能不能继续服务”。
- Tool fallback 是生产级 Agent 很重要的设计模式。
- 模型本身不负责存活性，但它可以在明确规则下参与故障处理决策。
