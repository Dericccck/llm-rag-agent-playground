# 12 Context Engineering 学习摘要

## 对应 Notebook
- `12-chat_summarization.ipynb`

## 这一节在做什么
这一节是在解决长对话里最常见的两个问题：
- 聊天历史越来越长，token 越来越贵
- 模型会逐渐忘掉前面重要信息

所以它做了一个“会压缩历史、会把关键事实写进 scratchpad”的 Agent。

## 这里要分清三个角色

### `qwen-max`
- 负责聊天
- 负责读用户偏好、生成行程建议
- 负责决定什么时候更新便签内容

### `ChatHistorySummarizationReducer`
- 负责压缩过长聊天历史
- 把旧对话总结成更短的摘要，减少 token 压力

### `ScratchpadPlugin`
- 负责把关键事实写到外部文件里
- 相当于 Agent 的便签本

## 这个 notebook 里的实现工序

### 1. 先建立 scratchpad
代码里定义了 `ScratchpadPlugin`，提供两个核心函数：
- `read_scratchpad()`
- `update_scratchpad()`

它背后实际对应一个 markdown 文件。

这意味着：
不是所有信息都只放在聊天历史里，关键事实可以额外写到外部文件中。

### 2. 再建立聊天历史压缩器
这里用了：
- `ChatHistorySummarizationReducer`

并设置两个关键参数：
- 超过多少条消息开始压缩
- 压缩后保留多少消息

它的工作方式大致是：
- 对话太长时
- 把前面历史总结成摘要
- 用摘要替代完整旧消息

### 3. 记录 token 使用
代码里还定义了 `TokenTracker`，专门记录：
- 每轮用了多少 token
- 什么时候发生了 history reduction

这样你能直观看到压缩机制到底有没有省成本。

### 4. 创建度假规划 Agent
然后创建旅行规划 Agent，并在提示词里强制规定：
- 对话开始先读 scratchpad
- 用户新偏好出现时立刻写入 scratchpad
- 完成任务后更新任务记录

### 5. 模拟长对话
接着 notebook 构造了一段较长的度假规划对话，例如：
- 用户先给预算和喜好
- 再让它生成巴厘岛行程
- 后来又改成希腊群岛
- 再继续问天气、行李、文化习俗、交通方式

### 6. 对话过程中同时做两件事

#### 一件事：缩减历史
- 当聊天太长，自动压缩旧对话

#### 另一件事：保留关键事实
- 用户偏好、任务状态写进 scratchpad

这样即使完整旧对话被压缩，Agent 仍然能保留重要记忆。

## 整个工序可以简化成
用户长对话 -> 关键偏好写进 scratchpad -> 聊天历史超阈值后自动摘要压缩 -> 后续回答时同时参考当前对话和便签内容 -> 在更低 token 成本下保持上下文连续性

## 这一节的关键收获
- 长对话管理不能只靠“把所有消息原样塞给模型”。
- 一个实用方案通常是两层：
  - 聊天历史摘要：保留整体语义
  - 外部 scratchpad：保留关键事实
- 这就是 context engineering 的核心味道：哪些信息该压缩，哪些信息必须保留。
